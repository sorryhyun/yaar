# Proposal: Google-Verified Publisher Identity + Device-Signed Publishing for YAAR Market

**Status:** Draft for review (revision 2)
**Decision:** Anchor publisher accountability in a **Google-verified market account**, authorize each
publication with a **registered device signature**, and guarantee **artifact integrity** end-to-end.
Do **not** use a provider (Claude/Codex) session ID as a credential, an identity source, or a
provenance gate.

> **What changed from revision 1.** The original draft made the authoring Claude session / Codex
> thread a resumable publishing constraint. Review concluded that a provider session ID cannot serve
> as an authentication credential, an identity assertion, or an "AI-authored" gate — the market can
> never verify a resume, and providers expose no identity lookup. The real underlying goal was
> **abuse accountability** ("if a bad app is uploaded, who submitted it?"), which is achieved by
> binding a **Google-verified identity** to the publisher account, not by tracing a session.
> Session/resume machinery is removed. See [Alternatives considered](#alternatives-considered).

---

## Summary

YAAR Market lets an agent publish an app it created, on behalf of a human publisher. Two questions
must be answerable, and each maps to a different mechanism:

| Question | Mechanism |
|---|---|
| **Who is accountable for this app?** | Google-verified YAAR Market publisher account |
| **Did that account authorize these exact bytes?** | Registered Ed25519 device signature over the artifact tuple |
| **Are these the bytes they authorized?** | Deterministic package + SHA-256, verified at publish and install |

Google identity gives a real-world, consented accountability anchor. The device signature gives a
remotely verifiable authorization that never transmits a secret. Artifact digests make every version
immutable and tamper-evident. Nothing in this design depends on a provider session ID.

We explicitly **do not** try to prove an app was authored by an AI. A human can hand-write code, run
it through any agent, and deploy it; that gate is both impossible and pointless. What matters is that
whoever published it is a **known, banned-if-abusive account** — which Google verification delivers.

---

## Goals

1. Let an agent publish a new app version to YAAR Market on behalf of a human publisher.
2. Bind every publisher account to a **Google-verified identity** (`sub` + verified email).
3. Authorize each publication with a **device signature** over an immutable
   `(publisherId, appId, version, manifestDigest, artifactDigest)` tuple.
4. Keep the publishing capability out of marketplace app iframes and ordinary web UI.
5. Make published versions immutable and verifiable at install time.
6. Support Claude and Codex behind one provider-neutral YAAR policy.
7. Provide an **accountability trail** sufficient to identify and ban an abusive publisher.
8. Require explicit user approval for the external publish action.

## Non-goals

- **Using a provider session ID as a credential, identity, or provenance signal.** It is an opaque
  locator with uncertain secrecy and no market-verifiable primitive.
- **Asking Anthropic/OpenAI to identify a session's owner.** No such lookup exists; providers are not
  identity providers for YAAR Market.
- **Proving an app was authored by an AI.** Unenforceable and trivially bypassed (paste code into an
  agent, ask it to deploy).
- **Using the Google token as a YAAR Market API credential.** The Google grant establishes identity at
  registration; the market issues its own scoped credentials thereafter.
- **Sending provider credentials to YAAR Market.** Claude/Codex secrets remain provider-only.
- **Publishing arbitrary files chosen by an iframe app.** Packaging is a host-side operation over a
  resolved app directory.
- **Defining marketplace ranking, billing, or moderation policy.** This proposal supplies verified
  identity, authorization, and artifact integrity for those later systems.

## Terminology

- **Publisher account** — a YAAR Market account whose identity is established by Google OIDC.
- **GoogleIdentity** — `{ sub, email, emailVerified }` obtained via consented Google login. `sub` is
  Google's stable, non-reassigned user identifier; it, not the email, is the durable key.
- **Device key** — an Ed25519 keypair generated by YAAR. Private key stays in the OS credential store;
  public key is registered to the publisher account.
- **Publish attestation** — the device-signed statement binding publisher, app, version, artifact
  digest, and a single-use market nonce.
- **Agent principal** — an authenticated YAAR `session`/`monitor`/`app` agent context backed by a
  server-minted agent token. Not an iframe principal.

## Security invariants

These are requirements, not later hardening.

1. Every publisher account is bound to a `GoogleIdentity` with `emailVerified = true`.
2. Provider (Claude/Codex) session IDs, transcripts, and credentials are never used for
   authentication, identity, or authorization, and are never sent to YAAR Market.
3. The device private key never leaves the OS credential store and never enters model context.
4. The Google `id_token`/access token is used only to establish identity at registration and is never
   stored as, or used as, the market publishing credential.
5. A publish is authorized for exactly one immutable tuple:
   `(publisherId, appId, version, manifestDigest, artifactDigest)`.
6. Every publish uses a single-use market nonce with a short expiry, included in the signed payload.
7. Publishing requires an **agent principal** with a server-minted token; a bare host HTTP call or an
   iframe cannot acquire it by setting an `agentId` header.
8. User confirmation happens after the final app/version/digest are known and before signing.
9. Published versions are immutable; any change requires a new version and digest.
10. Install verifies signed version metadata and the artifact digest **before** extraction/compilation.
11. Audit logs store the Google `sub`, device key id, stable hashes, and signed metadata — never
    provider tokens, provider session IDs, prompts, or transcripts.

## Why identity must be verified, not inferred

The tempting shortcuts all fail for the same structural reason: **the market can only observe what a
client sends, and a modified client can send anything.**

- A provider **session ID as a token** is a bearer string with poor secrecy (it appears in
  `session_logs/`, routing, banners), no market-side verification primitive, and no recovery story.
- **Resume-and-repeat a nonce** is unverifiable remotely: a modified client returns the nonce without
  resuming. Resume is a valid *local* provenance signal, never a *remote* credential.
- **Backchannel identity lookup** to Anthropic/OpenAI does not exist; providers are not IdPs.
- An **"AI authored this" gate** is impossible and bypassable.

The escape is standard: use a party **designed to assert identity with user consent** (Google as an
OIDC identity provider) for *who*, and **asymmetric signatures** (a registered device key) for *did
they authorize this*. The verifier holds only public values (a Google `sub`, a public key) — no shared
secret to store, transmit, or leak.

## Identity bootstrap

Publishing requires a one-time account + device setup, owned by the provider-neutral YAAR host.

### 1. Google-verified account

1. YAAR starts an **OAuth 2.0 / OIDC Authorization Code flow with PKCE** against Google, using a
   loopback redirect (`http://127.0.0.1:<port>`) as is standard for native/desktop apps.
2. Requested scopes: `openid email` (optionally `profile`). No Gmail/Drive scopes.
3. On return, YAAR validates the `id_token` (issuer, audience, signature, expiry, `nonce`) and reads
   `{ sub, email, email_verified }`. **`email_verified` must be true.**
4. YAAR registers a publisher account keyed by Google `sub` (durable) with the verified email as a
   display/contact value. If a publisher already exists for that `sub`, it is reused.

`sub` is the identity key, not `email` — Google can change a user's primary email, but `sub` is stable
and never reassigned.

### 2. Device key

5. YAAR generates an Ed25519 keypair in the OS credential store (Keychain / Credential Manager /
   libsecret).
6. YAAR registers the **public** key + a user-chosen device label to the publisher account.
7. The market returns scoped market credentials (access/refresh) for subsequent API calls; YAAR stores
   them in the OS credential store, never app storage.

The Google grant is now discharged — its job was to prove identity once. Ongoing authorization uses
the market credential (for account calls) plus the device signature (for publishing).

### Identity strength tiers

Google login alone proves control of a Google account, which throwaway accounts can satisfy. Escalate
per marketplace risk tolerance:

| Tier | Requirement | Deters |
|---|---|---|
| Base | Google `email_verified` | casual/one-off abuse |
| + Contact | phone verification, account-age / activity threshold | repeat abuse |
| + Cost | payment method or a small developer fee | determined abuse (a real-money anchor; the App Store / Play model) |
| + KYC | identity-document verification | high-risk categories |

Phase 1 ships the Base tier; higher tiers are additive and do not change the protocol.

### Suggested market scopes

| Scope | Purpose |
|---|---|
| `market:read` | Publisher profile, owned apps, publication status |
| `market:publish` | Prepare and finalize a new immutable version |
| `market:yank` | Hide a published version without deleting history |
| `market:transfer` | Transfer app ownership |

`market:publish` must not imply `market:transfer`.

## Publish protocol

```text
                        YAAR host                                    YAAR Market

 provider turn ──tool──> agent-token context
      │                        │
      │                        ├── resolve app dir by trusted appId
      │                        ├── deterministic package
      │                        └── SHA-256 artifact + manifest
      │                                     │
      │                                     ├──────── prepare ────────>
      │                                     │   market cred + digests
      │                                     │<──── nonce + upload URL ──
      │                                     │
      │<── tool result: pending publication ┤
      │
 same agent calls confirm_publish(publicationId)
      │                        │
      │        user confirm ── sign attestation (device key, over tuple+nonce)
      │                        ├──────── upload bytes ─────>
      │                        └──────── finalize (attestation+sig) ─>
      │                                              verify: sig, nonce,
      │                                              digest, ownership,
      │                                              publisher status
```

### Step 1 — agent requests publication (agent-principal only)

```ts
invoke('yaar://market/publications/my-app', {
  action: 'prepare',
  version: '1.2.0',
  releaseNotes: 'Add CSV import and fix dark mode.',
});
```

The handler is `agent-principal` only (see [Agent-only boundary](#agent-only-publishing-boundary)).
Invoking from an iframe, a bare host request, or a context without a minted agent token fails closed.

### Step 2 — YAAR builds the exact artifact

The host:

1. resolves the app directory by trusted `appId` lookup (never a path from the caller);
2. rejects path separators, traversal, symlink escapes, device files, and unexpected archive entry
   types;
3. validates `app.json`, version, permissions, bundles, required files;
4. runs the normal trusted typecheck/compile path;
5. produces a **deterministic** archive (normalized paths, ordering, timestamps, owners, modes);
6. computes `artifactSha256` and `manifestSha256`;
7. freezes the staged artifact until the pending publication completes or expires.

The archive is **not** rebuilt between approval and upload — the digest the user approves is the digest
the market receives. (Note: build determinism is best-effort across toolchain versions; the digest
attests "these exact bytes," not "reproducible from source by a third party.")

### Step 3 — market prepares a publication

YAAR sends its market credential and:

```json
{
  "appId": "my-app",
  "version": "1.2.0",
  "artifactSha256": "sha256:...",
  "manifestSha256": "sha256:...",
  "artifactBytes": 184231,
  "permissions": ["yaar://storage/"]
}
```

The market verifies publisher status and app ownership + version policy, then returns:

```json
{
  "publicationId": "pubver_...",
  "nonce": "base64url-random",
  "expiresAt": "2026-07-15T12:05:00Z",
  "uploadUrl": "https://object-store.example/..."
}
```

The nonce is single-use and bound server-side to the full proposed tuple.

### Step 4 — same agent confirms, user approves, host signs

The `prepare` result instructs the same agent to call:

```ts
invoke('yaar://market/publications/my-app', { action: 'confirm', publicationId: 'pubver_...' });
```

Before signing, YAAR shows a confirmation containing at least: publisher (Google email), app id,
version, artifact digest prefix + size, and any **new/expanded permissions** vs. the last published
version.

On approval, YAAR signs with the device key over deterministic JSON (e.g. RFC 8785 JCS):

```ts
interface PublishAttestationV1 {
  type: 'yaar.market.publish/v1';
  publisherId: string;
  deviceKeyId: string;
  appId: string;
  version: string;
  artifactSha256: string;
  manifestSha256: string;
  publicationId: string;
  nonce: string;          // host retrieves by publicationId; never becomes a reusable model secret
  issuedAt: string;
  expiresAt: string;
}
```

The nonce is fetched host-side by `publicationId` — the model never sees or echoes it.

### Step 5 — upload and finalize

YAAR uploads the frozen bytes, then sends the attestation + signature to finalize. The market:

1. verifies publisher account status (active, not suspended);
2. verifies the registered **device signature** against the stored public key;
3. checks nonce, publication id, expiry, single-use state;
4. rehashes the uploaded bytes and compares both digests;
5. re-validates manifest metadata and permission policy;
6. stores the immutable version + audit event;
7. sets status `processing` → `review` → `published` | `rejected`.

Finalize is idempotent by `publicationId`; replaying the same request returns the same result, and
changing any signed field fails.

## Accountability & abuse response

This is the section the whole design exists for.

### The accountability chain

```text
malicious app version
  └─ signed by a device key            (non-repudiation: publisher can't deny it)
       └─ device registered to a publisher account
            └─ publisher account bound to a Google-verified identity (sub + verified email)
                 └─ ⇒ we know which real Google account is responsible
```

Because each version carries a device signature over its exact digest, the publisher cannot claim "I
didn't publish that." Because the account is Google-verified, "which real account" resolves to a
concrete `sub`/email that YAAR Market holds directly — no dependency on Anthropic/OpenAI, no session
lookup.

### Response actions

- **Yank** a version (reversible removal from discovery) via `market:yank`.
- **Suspend** the publisher account — blocks all new publications immediately.
- **Revoke** a device key — invalidates pending publications from it; historical signatures still
  verify (for audit), but the key can't sign new versions.
- **Ban** the Google `sub` — prevents re-registration under the same identity. Escalate to higher
  identity tiers (payment/KYC) to make re-entry under a fresh throwaway account costly.

### What this does and does not prove

- **Does:** identify the Google account behind a version, hold it non-repudiably responsible, and ban
  it. Sufficient to deter and evict abusers at the level most app marketplaces operate.
- **Does not:** by itself establish real-world legal identity beyond what Google verified. For that,
  add the KYC tier. It also does not prove *who wrote* the code (nor should it) — only who is
  accountable for publishing it.

### Audit event shape

```text
actorUser       Google sub (+ verified email at time of action)
actorDevice     registered device key id
action          prepare | finalize | publish | yank | suspend | revoke | transfer
appId, version
artifactSha256, manifestSha256
signature       device signature (verifiable later)
```

No provider session ids, prompts, or transcripts are stored.

## Agent-only publishing boundary

The product may omit a "Publish" button from the Market Apps UI. The server rule is stronger than UI
omission:

1. Add `access: 'agent-principal'` to the resource-handler access tiers, parallel to
   `session-principal`.
2. `agent-principal` requires a restored agent role and a server-minted agent token.
3. A bare host or iframe verb request has no qualifying context and is denied.
4. Market credentials and device-signing operations live only in the server feature, never in an
   iframe SDK.

This does not claim a human can never automate the endpoint (they can instruct an agent, and the host
owner can modify the software). It ensures ordinary marketplace apps, web requests, and unbound agents
cannot publish with the user's market account.

## Installer integrity

Publishing identity is worthless if install accepts unverified bytes. The current path fetches
`/api/apps/{appId}/download`, writes to disk, and extracts before any verification. Install must
change to:

1. fetch **signed** version metadata;
2. select an **immutable version**, not an unqualified mutable archive;
3. download to staging;
4. verify byte length and SHA-256 **before** extraction;
5. validate archive entries without trusting `tar` to be traversal-free;
6. verify `app.json` matches the signed manifest digest;
7. show permission differences vs. the installed version;
8. compile and atomically activate only after all checks pass.

Identity answers "who authorized this version?"; digest verification answers "are these the exact bytes
they authorized?" Both are required.

## Suggested market API

```text
GET  /oauth/google/start                       begin Google OIDC (PKCE, loopback redirect)
POST /oauth/google/callback                    validate id_token → create/reuse publisher, issue market creds
POST /v1/publisher/devices                     register public device key
DELETE /v1/publisher/devices/{deviceId}        revoke device

POST /v1/publications/prepare                  digests + metadata → nonce + upload URL
PUT  {presignedUploadUrl}                       artifact bytes
POST /v1/publications/{id}/finalize            attestation + signature
GET  /v1/publications/{id}                      status

POST /v1/apps/{appId}/versions/{version}/yank  reversible removal from discovery
POST /v1/publisher/{id}/suspend                 admin/abuse action
POST /v1/apps/{appId}/transfer                  ownership transfer (market:transfer)
```

The market credential authenticates the account; the device signature authorizes the exact
publication. Requiring both means a stolen bearer token alone cannot publish a substituted artifact.

## Publication state machine

```text
none
  └─ prepare ──> awaiting_confirmation
                    ├─ expires/cancel ──> expired
                    └─ agent confirm
                           └─ user approval ──> signed
                                                  ├─ upload failure ──> retryable
                                                  └─ finalize ──> processing
                                                                    ├─ review
                                                                    ├─ rejected
                                                                    └─ published
```

Rules:
- One live pending publication per `(publisherId, appId, version)`.
- Pending state freezes artifact path, digest, and nonce.
- A changed source tree requires cancel + new prepare; it never mutates pending state.
- Device revocation or publisher suspension invalidates pending/retryable publications.

## Failure behavior

| Failure | Required result |
|---|---|
| `email_verified` is false at registration | Refuse account creation |
| Wrong agent / iframe / bare HTTP calls publish | Deny (no agent-principal token) |
| User rejects confirmation | Cancel pending publication, invalidate nonce |
| Source changes after prepare | Keep frozen artifact or cancel; never rebuild under approved digest |
| Upload interrupted | Retry same frozen bytes while nonce valid |
| Finalize response lost | Retry idempotently by `publicationId` |
| Market bearer token stolen | Device signature still required; revoke grant/device |
| Device private key stolen | Revoke device, rotate; audit affected versions |
| Market database leaks | Contains Google `sub`s, public keys, and signed metadata — no signing secret |
| Abusive app published | Yank version, suspend/ban publisher, ban Google `sub` |

## Rollout

### Phase 0 — integrity foundation
Immutable versions, deterministic package + SHA-256, safe archive inspection, digest verification
before install extraction, permission diff on update. Independently valuable; do this first.

### Phase 1 — Google identity + device signing
Google OIDC (PKCE, loopback), publisher/device tables, Ed25519 registration/rotation/revocation,
host-only credential storage, prepare/upload/finalize with signed artifact tuple, agent-principal URI
tier. This delivers the full security and accountability model.

### Phase 2 — accountability & moderation
Pre-publish review gate, yank/suspend/ban tooling, audit surfacing, higher identity tiers
(phone/payment/KYC) as risk requires.

### Phase 3 — lineage & recovery (optional)
Ownership transfer, device rotation UX, optional remote YAAR Market MCP server reusing the same OAuth
and publication API.

## Acceptance criteria

1. A publisher account can be created only with a Google `email_verified = true` identity.
2. A newly created app can be published from an active agent after user confirmation.
3. Publishing works identically whether the app was authored via Claude or Codex — no session is
   consulted.
4. A bare HTTP client or marketplace iframe cannot publish.
5. Changing one byte after approval causes finalize or install verification to fail.
6. YAAR Market never receives a provider session ID, transcript, or provider credential.
7. Given an abusive version, an admin can resolve it to a Google `sub`, ban it, and prevent
   re-registration under the same identity.
8. Revoking a device prevents new publications from it without breaking historical signature
   verification.
9. Retrying finalize after a lost response does not create a duplicate version.
10. An installer verifies the immutable version digest before extracting any archive entry.

## Alternatives considered

### Provider session ID as bearer token
Rejected. Opaque locator with provider-specific lifecycle, poor secrecy (logged in `session_logs/`,
routing, banners), and no market-side verification primitive.

### Resume-and-repeat a market nonce
Rejected as a remote anchor. A modified client repeats the nonce without resuming; the market cannot
witness a resume. Valid only as a *local* provenance check, which this design does not require.

### Send provider session ID to the market for "the agent to self-validate"
Rejected — strictly worse. It stores a raw provider locator server-side (breach target), transmits it
on every publish (replayable), and still reduces to a bearer check the market cannot tie to a live
session.

### Embed a secret word in the conversation and reproduce it via resume
Rejected. Still a bearer secret, placed in the most-logged surface (the transcript), and LLM
reproduction is non-deterministic. The market only ever sees a string.

### Backchannel identity lookup to Anthropic/OpenAI
Rejected — not offered, and would be a severe privacy violation. Providers are not YAAR Market IdPs.

### "AI-authored" provenance gate
Rejected. Cannot be cryptographically established, and a human trivially satisfies it by running
hand-written code through an agent. It filters nothing and only inconveniences honest users.

### Derive the device private key from the session ID
Rejected — catastrophic. It downgrades the signing key to the secrecy level of a session ID (which is
logged widely), so a single log leak yields full, permanent signature forgery. A private key must be a
kept-secret high-entropy value: a random seed in the OS keychain, not a widely-logged locator.

### Google login as the market API credential (no device key)
Rejected as insufficient alone. Identity ≠ per-publication authorization; a stolen bearer token would
suffice to publish a substituted artifact. Google establishes *who*; the device signature authorizes
*what*.

## Open decisions

1. **Identity tier for launch:** Base (Google verified) only, or require payment/KYC before public
   discovery? Recommend Base for Phase 1, payment tier before open public listing.
2. **Handle allocation:** first-come vs. reserved/verified handles to prevent impersonation of known
   brands. Recommend reserving obviously-impersonating handles.
3. **Review gate:** publish immediately after automated checks, or enter moderation review? Recommend
   review-by-default for public discovery until scanning is mature.
4. **Device key storage fallback:** if the OS keyring is unavailable, refuse publishing or use an
   encrypted file protected by a user secret? Recommend refuse by default; design fallback explicitly.
5. **Multi-device:** allow multiple registered devices per publisher from the start? Recommend yes —
   it is free with per-device keys and avoids lockout.

## Recommendation

Build in the order **artifact integrity → Google identity + device signing → accountability/moderation**.

Treat Google login as the *identity* anchor (who is accountable), the registered device signature as
the *authorization* credential (did they approve these exact bytes), and SHA-256 digests as the
*integrity* guarantee (are these the bytes). These three verifiable mechanisms fully replace the
session-binding design, which could only ever have been local provenance dressed up as security.
