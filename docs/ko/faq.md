# FAQ — YAAR는 왜 이런 모습인가?

> [English version](../faq.md)

사람들이 이 프로젝트를 처음 보고 실제로 묻는 질문들에, 솔직하게 답합니다. 작동 원리 자체가 궁금하다면 [OS 아키텍처 맵](../architecture/os_architecture.md)과 [모니터 & 윈도우 가이드](../architecture/monitor_and_windows_guide.md)부터 보세요.

---

### 한 문장으로 말하면, 이게 뭔가요?

화면에 무엇이 나타날지를 AI가 직접 결정하는 바탕화면입니다. 사용자는 언제나 준비된 입력창 하나에 타이핑만 하면 되고, 에이전트는 문단을 써서 답하는 대신 윈도우를 열고, 앱을 만들고, 그것들을 서로 연결하는 방식으로 응답합니다.

---

### 왜 GUI인가요? 에이전트 도구는 다 TUI나 채팅창이던데.

텍스트 스트림은 모든 것을 직렬화하는데, 에이전트가 하는 일은 원래 직렬적이지 않기 때문입니다.

채팅 기록은 한 번에 한 가지만, 일어난 순서대로만 보여줄 수 있습니다. 하지만 에이전트 세션은 본래 *상태*를 만들어냅니다 — 다음 질문을 하는 동안에도 계속 떠 있어야 할 차트, 계속 열어두고 싶은 파일 브라우저, 서로 다른 가상 바탕화면에서 돌아가는 백그라운드 작업 세 개. 윈도우는 그 상태를 있는 그대로 표현하는 방식입니다 — 지속되고, 병렬적이고, 개별적으로 주소를 붙일 수 있습니다.

GUI는 출력 장치일 뿐 아니라 *입력* 장치이기도 합니다. 이미지를 붙여넣거나, 오른쪽 클릭 드래그로 스케치하거나, AI가 만든 윈도우 안의 버튼을 클릭하거나, 파일을 앱 위에 드래그할 수 있습니다. 이 모든 것이 터미널에서는 표현하기 어색하거나 아예 불가능한, 에이전트에게 보내는 메시지입니다.

그리고 현실적으로, LLM은 HTML/JS UI를 만드는 데 정말로 능숙합니다. "작동하는 인터페이스로 응답하라"는 능력은 이미 거기 있는데, 채팅 인터페이스는 그걸 담을 곳을 애초에 모델에게 주지 않을 뿐입니다.

(그래도 TUI스러운 탈출구는 남아 있습니다. `Shift+Tab`을 누르면 에이전트의 원시 추론과 도구 호출을 실시간으로 스트리밍하는 CLI 패널이 열려서, 내부 동작을 직접 지켜보고 싶을 때 쓸 수 있습니다.)

---### 근본적으로는 에이전트 오케스트레이션인데, 왜 "OS" 전체를 만드나요?

정직하게 하다 보면 에이전트 오케스트레이션은 결국 OS의 문제들을 계속 재발명하게 되기 때문입니다 — 그래서 YAAR는 그때그때 더 허술한 답을 새로 만드는 대신, OS가 이미 내놓은 답을 그대로 빌려 씁니다:

| 오케스트레이션 문제 | YAAR가 재사용하는 OS의 답 |
|---|---|
| 에이전트는 많은데 자원은 한정됨 | 프로세스 테이블 + 스케줄러 (`AgentPool`, 큐 정책, 레이트 버짓) |
| 에이전트끼리 서로 밟고 지나가면 안 됨 | 프로세스 격리 + 특권 계층 (세션 에이전트 ≈ root, 앱 에이전트는 샌드박스) |
| 에이전트가 세상에 뭔가를 해야 함 | 임의 접근 대신 시스템 콜 (MCP 도구) |
| 에이전트끼리 서로 대화해야 함 | IPC (앱 프로토콜, relay, 다이렉트 메시지) |
| 기능은 설치 가능해야 함 | 패키지 매니저 (앱은 폴더이고, 마켓이 이를 설치함) |
| 작업은 연결이 끊겨도 살아남아야 함 | 세션은 브라우저 탭과 무관하게 지속됨 |

OS라는 틀은 브랜딩이 아닙니다 — 스케줄링, 권한, 주소 지정, 라이프사이클 등 멀티 에이전트 시스템이 정확히 부딪히는 문제들에 대해 50년간 검증된 답을 가진 설계 어휘입니다. 개념 대 개념의 전체 매핑은 [OS 아키텍처 맵](../architecture/os_architecture.md)을 참조하세요.

범위를 분명히 하자면, YAAR는 여러분의 운영체제를 대체하려는 게 아닙니다. 로컬 서버 하나에 브라우저 탭 하나일 뿐입니다. 여기서 "OS"는 부트 파티션이 아니라 하나의 형태(shape)입니다.

### 왜 웹/HTML인가요? 네이티브 앱은 왜 아닌가요?

중요도가 높은 순서대로 세 가지 이유가 있습니다:

1. **단일 파일 HTML은 우리가 가진 것 중 샌드박스화하기 가장 좋은 UI 런타임입니다.** 모든 YAAR 앱은 iframe에서 렌더링되는 하나의 자체 완결형 HTML 파일로 컴파일됩니다. 이는 앱별 경계, 손쉬운 배포(앱이 곧 파일 하나입니다), 그리고 핫스왑 가능한 윈도우를 제공합니다 — 플러그인 ABI도, 플랫폼별 네이티브 패키징도 필요 없이 말이죠.
2. **모델이 가장 잘하는 포맷이기 때문입니다.** LLM에게 작동하는 HTML/CSS/JS를 뽑아내라고 하는 것은 학습 분포에서 가장 강한 부분을 정확히 건드립니다. Qt나 SwiftUI를 뽑아내라고 하면 그렇지 않습니다.
3. **브라우저 프론트엔드는 공짜로 도달 범위를 넓혀줍니다.** 같은 서버가 노트북에서도 렌더링되고, 원격 모드의 QR 코드를 통해 별도 클라이언트 코드 없이 휴대폰에서도 렌더링됩니다.

그 아래 스택은 의도적으로 지루합니다. 로컬 Bun/TypeScript 서버가 모든 상태를 소유하고, 브라우저는 그저 디스플레이 서버일 뿐입니다.

### 에이전트는 실제로 어떻게 뭔가에 접근하나요? 도구가 50개쯤 있나요?

다섯 개입니다. `describe` · `read` · `list` · `invoke` · `delete`.

시스템 안의 모든 것 — 윈도우, 파일, 앱, 설정, 알림, 다른 에이전트 — 은 `yaar://` URI로 주소를 붙일 수 있고, 이 다섯 개의 동사는 그중 무엇에든 작동합니다:

```
list('yaar://apps')                          → what's installed
describe('yaar://apps/slides-lite')          → its schema and supported verbs
read('yaar://storage/data.csv')              → file contents
invoke('yaar://windows/chart', {...})        → open/update a window
delete('yaar://windows/old-panel')           → close it
```

핵심은 컨텍스트 경제성입니다. 전형적인 MCP 구성은 기능 하나당 도구 하나를 등록하므로, 앱을 설치할 때마다 도구 목록 — 그리고 시스템 프롬프트 — 이 계속 커집니다. YAAR의 시스템 프롬프트는 앱이 3개든 100개든 항상 8K 토큰 이하로 유지되는데, 기능 발견이 프롬프트 조립 시점이 아니라 런타임(`describe`)에 일어나기 때문입니다. 전체 레퍼런스는 [URI 기반 리소스 주소 지정](../architecture/verbalized-with-uri.md)을 참조하세요.

### AI가 코드를 작성하고 실행한다는데, 그걸 왜 믿어야 하나요?

믿을 필요가 없습니다 — 설계 자체가 여러분이 믿지 않는다는 것을 전제로 합니다:

- **범위가 제한된 파일시스템.** AI의 파일 접근은 기본적으로 `storage/`, `config/`, `apps/`, `session_logs/`로 한정됩니다. 이 밖의 폴더는 명시적으로 마운트해야 하며(읽기 전용도 지원됩니다).
- **하나의 접근 게이트.** 모든 HTTP 라우트는 *누가 호출하는지*(바탕화면 프린시펄인지 앱 프린시펄인지)와 *어떤 URI + 동사*를 원하는지를 동일한 검사를 통해 판별합니다. 라우트가 각자 자기만의 권한 로직을 만들어내지 않습니다.
- **앱 권한 범위.** 앱은 자동으로 부여되는 자기 네임스페이스(`yaar://apps/self/…` — 스토리지, 데이터베이스, 페르소나)와 `app.json`이 선언한 것만 건드릴 수 있고, 그 외에는 아무것도 건드릴 수 없습니다.
- **네트워크 허용목록 + SSRF 가드.** 외부로 나가는 HTTP는 `config/curl_allowed_domains.yaml`에 있는 도메인으로 제한되며, 새 도메인은 여러분의 승인이 필요하고, 내부망 주소는 차단됩니다.
- **에이전트 계층.** 위험한 네임스페이스(`yaar://session/*`, 실제 브라우저 제어 포함)는 특권을 가진 세션 에이전트만 접근할 수 있습니다. 그 외에는 기본적으로 모두 거부됩니다.
- **오리진 격리.** 앱은 바탕화면과 다른 브라우저 오리진에서 서빙되므로, 앱이 바탕화면 수준의 요청을 위조할 수 없고 `window.parent`로 바탕화면에 닿는 것도 브라우저가 막습니다 — 로컬에서는 `localhost` / `127.0.0.1`, Tailscale에서는 `…ts.net` / `…ts.net:8443`입니다. [리모트 모드 → 앱 오리진 격리](./remote_mode.md#앱-오리진-격리)를 참고하세요.

### 앱은 왜 그냥 폴더인가요?

대부분의 AI 툴링에서는 기능 하나가 네 개의 레지스트리에 흩어져 있기 때문입니다 — AI를 위한 스킬 파일, 서버를 위한 플러그인, 프론트엔드를 위한 UI 컴포넌트, 어딘가의 설정 파일. YAAR에서는 폴더 하나가 이 전부를 담습니다:

```
apps/slides-lite/
  app.json        ← metadata + permissions
  SKILL.md        ← what the AI reads to know how to use it
  AGENTS.md       ← optional: a dedicated agent for this app
  src/main.ts     ← the UI + logic
  dist/index.html ← the build: one self-contained file
```

폴더를 넣으면 → 설치됩니다. 지우면 → 사라집니다. 등록 코드 같은 건 없습니다. 이는 또한 앱이 자신만의 에이전트를 함께 담을 수 있다는 뜻이기도 합니다. 앱 윈도우와 상호작용하면 그 앱을 위한 영속 앱 에이전트가 생성되어 모니터 에이전트에게 메시지를 보낼 수 있고 — `controls`가 선언되어 있다면 *다른* 앱을 직접 조작할 수도 있습니다(Dev Tools가 Browser 앱을 조작해 앱을 처음부터 끝까지 빌드하고 테스트하는 식으로).

### 어떤 AI가 뒤에서 돌아가나요? 또 다른 구독료를 내야 하나요?

YAAR는 여러분이 이미 가지고 있는 에이전트 런타임의 프론트엔드입니다. **Claude Code**(Agent SDK 경유) 또는 **Codex**(JSON-RPC 경유)를 서브프로세스로 실행하며, 여러분이 이미 로그인해둔 계정을 그대로 씁니다. 별도의 YAAR 계정도, API 키도, 호스팅 서비스도 없습니다 — 서버는 여러분의 기기에서 돌아가고, 대화 내용은 여러분이 선택한 프로바이더가 원래 보내던 곳으로만 가지, 그 외에는 어디로도 가지 않습니다. 프로바이더별 동작 차이는 [claude_codex.md](../reference/claude_codex.md)에 문서화되어 있습니다.

### 그냥 아티팩트 딸린 채팅이거나 컴퓨터 사용 에이전트 아닌가요?

가까운 이웃이지만 전제가 다릅니다:

- **채팅 + 아티팩트**는 대화에 UI 출력을 덧붙이는 방식입니다. YAAR에서는 관계가 뒤집힙니다 — 바탕화면이 1차 매체이고 대화는 입력 수단입니다. 윈도우는 지속되고, 주소가 붙으며(`yaar://windows/...`), 개별적으로 메시지를 받을 수 있고, 세션을 넘어 살아남습니다.
- **컴퓨터 사용 에이전트**는 AI를 사람을 위해 만들어진 화면 앞에 세워놓고 픽셀과 클릭을 더듬거리게 만듭니다. YAAR는 AI에게 *AI를 위해* 만들어진 환경을 줍니다 — 모든 것이 스키마를 가진 URI이므로, 시스템에 뭔가를 하는 것은 스크린샷 고고학이 아니라 타입이 있는 호출이 됩니다. (실제 브라우징이 필요할 때는 게이팅된 `yaar-web` SDK가 따로 있습니다.)

### 이름이 왜 "YAAR"인가요?

**Y**ou **A**re **A**bsolutely **R**ight(당신 말이 전적으로 맞습니다) — 에이전트를 많이 써본 사람이라면 수백 번은 읽어봤을 그 문장입니다. 어차피 AI가 그 말을 할 거라면, 차라리 바탕화면까지 운영하게 하자는 거죠.
