# YAAR Bridge — Implementation Plan & Build Record (Slices 0–2)

Authoritative build record for the first three slices of the **YAAR Bridge** companion extension —
the T1/T2 tiers of [`docs/extension_bridge_proposal.md`](./docs/extension_bridge_proposal.md)
(itself Phase 4 of [`docs/browser_substrate_proposal.md`](./docs/browser_substrate_proposal.md)).
The proposal's tier/consent thesis stays authoritative; the concrete T1/T2 implementation lives
**here**.

## Status

| Slice | Tier | State |
|-------|------|-------|
| **Slice 0** — bare transport (MV3 extension + `/bridge` WS route, log-only) | — | ✅ **Done** |
| **Slice 1** — read-only tab feed (`yaar://browser/*`, "Real Tabs" app) | T1 Observe | ✅ **Done & verified** live against the real extension + real Chrome |
| **Slice 2** — manage verbs (`focus/close/group/move`) + tracking cursor | T2 Manage | ✅ **Done** (as-built deltas below) |

> **Sequencing rationale.** The proposal's "Phase 1" silently bundled three jobs: the transport, the
> first-ever `yaar://browser/*` handler namespace, and a demo app. We split them. Slice 0 de-risked
> the transport (the only genuinely novel risk — MV3 service-worker WebSocket lifetime). Slice 1
> built the read-only tab feed (**T1 Observe**). Slice 2 introduces the `BrowserProvider` and
> mutation verbs (**T2 Manage**). The `ExtensionBridgeBrowser` provider — a heavy CDP-shaped
> abstraction — is deliberately deferred to Slice 2, because listing tabs (T1) needs no provider at
> all.

## Slice 1 — T1 Observe: the live tab feed ✅ DONE & VERIFIED

**Goal:** a real, logged-in tab list from the user's everyday Chrome, published on
`yaar://browser/tabs`, pushed to subscribers on change, and rendered by a demo app.
**No page content. No mutation. No `BrowserProvider`.**

> **Verified live** against the real extension + real Chrome: the "Real Tabs" app renders the user's
> actual tabs with a `bridge · N` badge, an `active` badge on the focused tab, and a `self` badge on
> YAAR's own tab. 15 tests green; full typecheck clean.
>
> **As-built deltas from the spec below** (both discovered during the build):
> 1. **`resolveUri` needed a fix.** `yaar://browser/*` parsed as a valid authority but `resolveUri()`
>    returned `null` for it, so a registered handler would never fire. Added `browser` to the
>    root-kind fallback + bare-authority regex in `handlers/uri-resolve.ts`.
> 2. **Tabs handler registered as a prefix** (`yaar://browser/tabs/`), not exact — the prefix matcher
>    treats `uri === pattern-without-slash` as a match, so one handler serves both the collection and
>    `yaar://browser/tabs/{id}`.
> 3. The demo app is **`apps/browser-tabs/` ("Real Tabs")**. `BRIDGE_PROTOCOL_VERSION` lives in
>    `packages/shared/src/bridge.ts`; on mismatch Slice 1 **warns and accepts** (hard refuse deferred
>    to a later slice, per the extension's own version note).

### 1.1 Bridge connection state (server) — `features/browser/bridge.ts` (new)

A tiny singleton holding the *current* bridge state — the one authoritative in-memory model the WS
route writes and the handler reads. Deliberately **not** a `BrowserProvider`; it is just observed
state.

- `BridgeHub` (singleton, mirroring the `subscriptionRegistry` export style):
  - `setConnection(ws, hello)` / `clearConnection()` — called by the `/bridge` WS `open`/`close`.
  - `isConnected(): boolean`, `getFidelity(): 'os-signals' | 'bridge'` — `'bridge'` when connected
    (the `fidelity` field the proposal §3 requires so UIs can show what's available).
  - `updateTabs(tabs: BridgeTab[])` — store the latest snapshot; on change call
    `subscriptionRegistry.notifyChange('yaar://browser/tabs')` **and**
    `notifyChange('yaar://browser/presence')` (presence forward-compat, even if only `tabCount` for
    now).
  - `getTabs(): BridgeTab[]`.
  - Annotate `isSelf` on any tab whose URL is YAAR's own origin (reuse `isYaarOriginUrl` from
    `guards.ts`) — the proposal's "YAAR tab is one target among targets" principle.
- `BridgeTab` type: `{ id, url, title, active, audible?, windowId?, isSelf? }` — the T1 metadata
  set from the proposal table (§2), **tab-level only, never content**.

> Why a separate `bridge.ts` and not fold into the handler: the WS route (a different entry point)
> and the verb handler both need this state, so it lives in `features/`, imported by both — the same
> pattern as `features/session/browser.ts` feeding `handlers/session.ts`.

### 1.2 `/bridge` WS route (server)

1. **`WsData` discriminant** — `websocket/server.ts:31`: add `kind: 'frontend' | 'bridge'`
   (default `'frontend'` for the existing `/ws` path so nothing changes).
2. **Upgrade branch** — `http/server.ts:91`, add alongside `/ws`:
   ```ts
   if (url.pathname === '/bridge') {
     if (!checkWsAuth(url)) return new Response('Unauthorized', { status: 401 });
     const success = server.upgrade(req, {
       data: { kind: 'bridge', connectionId: generateConnectionId(), sessionId: null, monitorId: null },
     });
     if (success) return undefined;
     return new Response('Bridge upgrade failed', { status: 500 });
   }
   ```
3. **Handler branch** — `websocket/server.ts` `createWsHandlers`: at the top of `open`/`message`/
   `close`, `if (ws.data.kind === 'bridge') return handleBridge*(ws, ...)`. Keep bridge logic in a
   small `websocket/bridge-handlers.ts` to avoid bloating the frontend handlers:
   - `open` → nothing yet (wait for `hello`).
   - `message` → parse `BridgeMessage` (see 1.4); on `hello` → version-check + `BridgeHub.setConnection`;
     on `tabs` → `BridgeHub.updateTabs`.
   - `close` → `BridgeHub.clearConnection()` → `notifyChange` (feed downgrades to `os-signals`/empty).

### 1.3 `yaar://browser/tabs` handler (server) — `handlers/browser.ts` (new)

Model on `handlers/session.ts:119`. **Read-only in Slice 1** (`verbs: ['describe', 'read', 'list']`,
**no `invoke`**). No `access: 'session-principal'` — T1 is monitor-agent + granted-app readable, per
proposal §2. (App reads still pass through `/api/verb` default-deny; the app must declare
`yaar://browser/tabs` in `app.json` `permissions` — existing enforcement, no new code.)

- `read('yaar://browser/tabs')` → `okJsonResource` with `{ fidelity, connected, tabs }`.
- `read('yaar://browser/tabs/{id}')` → single tab (prep for Slice 2 verbs on the same URI).
- `list('yaar://browser/tabs')` → `okLinks` of `yaar://browser/tabs/{id}`.
- `read('yaar://browser/presence')` → `{ fidelity, connected, tabCount, activeTab }` — the shared
  surface the OS-presence proposal also targets; Bridge simply provides the richer `fidelity:'bridge'`
  input.
- Register in `initRegistry()` at `handlers/index.ts:53`-ish: `registerBrowserHandlers(registry)`.

### 1.4 Shared message schema — `packages/shared/src/bridge.ts` (new)

Zod (v4) schemas for the WS contract, exported from the shared package so both the server route and
(via a hand-copy or build step) the extension agree:
- `BridgeHello` — `{ type: 'hello', protocolVersion: number, browser: { name, version }, tabCount }`.
- `BridgeTabs` — `{ type: 'tabs', tabs: BridgeTab[] }`.
- `BridgeMessage = BridgeHello | BridgeTabs` (discriminated union on `type`).
- **Versioned handshake** (proposal §5 "protocol drift"): server checks `protocolVersion` against a
  `BRIDGE_PROTOCOL_VERSION` constant; on mismatch, warn + refuse (don't half-speak an old dialect).

### 1.5 Extension (T1 additions) — `extension/`

Building on Slice 0's skeleton:
- `manifest.json` `permissions: ["tabs"]` (already present from Slice 0).
- `background.js`: register `chrome.tabs.onCreated/onUpdated/onRemoved/onActivated` → debounce
  (~150ms) → send a fresh `{ type: 'tabs', tabs }` snapshot over the socket. Send once on connect
  after `hello`.
- Send **snapshot, not deltas** in Slice 1 — simplest correct thing; deltas are a later optimization.

### 1.6 Demo — "Tabs" app — `apps/browser-tabs/` (new)

- `app.json`: `permissions: ["yaar://browser/tabs"]`, small window.
- `src/main.ts` (Solid + `@bundled/yaar`): `subscribe('yaar://browser/tabs')` → render live list
  (title, favicon-less for now, `active` badge, `isSelf` badge). Proves the whole loop end-to-end and
  is the shippable demo from proposal §7 Phase 1.

### Slice 1 done =
Real tabs from your everyday Chrome appear live in a YAAR window and update as you open/close/switch
tabs, with **zero** page-content access. Add `tests/bridge.test.ts` (hub state transitions +
`notifyChange` fired; schema round-trip; version mismatch refused).

## Slice 2 — T2 Manage: window-manager verbs over real tabs ✅ DONE

**Goal:** `invoke` on `yaar://browser/tabs/{id}` to `focus | close | group | move` real tabs —
"YAAR manages your browser like an OS manages windows." This is the first slice that sends commands
*back down* the socket. Plus a **tracking cursor**: whenever YAAR acts on (or watches) a real tab,
the extension paints a transient pulsing pill overlay on that page + flashes its toolbar badge, so
the user *sees* the OS reach into their browser.

> **As-built deltas from the spec below** (all discovered/decided during the build):
>
> 1. **No `ExtensionBridgeBrowser: BrowserProvider`.** The `BrowserProvider` interface is entirely
>    `BrowserSession`/CDP-shaped (`createSession`, `getStats`, adopted-tab maps…); T2 traffics in
>    `BridgeTab` ids over a socket, so implementing it would mean fabricating fake sessions and ~10
>    no-op methods for zero T2 value. Instead the **command transport lives in `BridgeHub`**
>    (`sendCommand()` with a `requestId` correlation map, `resolveCommand()`, `sendActivity()`), which
>    already owns the connection. The full provider is deferred to **T3**, where CDP actually arrives
>    and the interface earns its shape. No `getBridgeBrowser()` factory was added.
> 2. **A focused `enforceTabControlGuard`** (guards.ts) instead of routing a fake session through
>    `enforceBrowserGuards`. It reuses the exact consent primitives (`isYaarOriginUrl` self-refusal +
>    origin-based `ensureTabControlConsentForUrl`, refactored out of the session-based path). Same
>    consent thesis, honest shape.
> 3. **`focus` is not a mutation.** Bringing a tab forward is what the user does by clicking a tab —
>    no page interaction, no data exposure — so it needs no per-origin consent and is allowed even on
>    YAAR's own tab. Only `close`/`group`/`move` are gated + self-refused (`MUTATING_TAB_ACTIONS`).
>    A fifth action, **`track`**, is a pure observation cue (shows the cursor, mutates nothing).
> 4. **Version handling is graceful, not a hard refuse.** A v1 extension keeps feeding tabs (T1
>    reads still work — Slice 1's warn+accept stands); `sendCommand` refuses only *commands* when the
>    connected `protocolVersion < BRIDGE_COMMAND_MIN_VERSION (2)`. Old extension → clean "update me"
>    error on `invoke`, not a broken feed. `BRIDGE_PROTOCOL_VERSION` bumped `1 → 2`.
> 5. **`handlers/browser.ts` imports `getSessionId` lazily** (`await import(...)` inside `invoke`).
>    Pulling agent-context's AsyncLocalStorage getters into the handler's eager module graph
>    mis-links `getAgentRole` under Bun's loader (the same cycle the uri-registry resolver injection
>    sidesteps); deferring to call-time keeps it acyclic and keeps the test files co-runnable.
> 6. **App permission is now `yaar://browser/tabs/`** (trailing slash) so the Real Tabs app can
>    `invoke` on `yaar://browser/tabs/{id}` — the prefix form still covers reading the collection.
> 7. 18 new tests green (schema round-trips, `sendCommand` requestId correlation + disconnect +
>    old-version refusal, guard self-target refusal, handler invoke paths); full typecheck clean.
>    (The repo-wide `bun test` segfault + `getAgentRole` error is **pre-existing on master** — a Bun
>    1.3.11 full-suite quirk, unrelated to this slice.)

### 2.1 `ExtensionBridgeBrowser` — `lib/browser/extension-bridge-browser.ts` (new)

Implements `BrowserProvider` (`lib/browser/types.ts:40`) **directly — not** extending
`CdpBrowserProvider` (which assumes a CDP debug port the extension doesn't expose at T2).
- `controlsUserBrowser = true` → `enforceBrowserGuards` (`guards.ts:90`) automatically gates every
  mutation behind per-origin consent + self-target refusal. **Free consent layer.**
- Command transport: a `sendCommand(cmd): Promise<result>` that writes a `BridgeCommand` frame to the
  connected bridge socket (via `BridgeHub`) and awaits a correlated `BridgeCommandResult` (add a
  `requestId` correlation map). T2 commands are `focus/close/group/move` only — thin `chrome.tabs`/
  `chrome.tabGroups` glue on the extension side.
- `isAvailable()` → `BridgeHub.isConnected()`.
- Most `BrowserProvider` session methods (`createSession`, `consumeAdoptedTabs`, `syncExistingTabs`,
  CDP session maps) are **not needed for T2** — implement as minimal no-ops/throws with a clear
  "T3 not yet" message. They light up only when T3 (`chrome.debugger` CDP relay) lands.
- Factory: add `getBridgeBrowser()` next to `pool.ts:128`.

### 2.2 T2 verbs on the tab handler — extend `handlers/browser.ts`

- Add `'invoke'` to the `yaar://browser/tabs/{id}` verbs, with `invokeSchema`
  `{ action: 'focus'|'close'|'group'|'move', ... }`.
- `invoke` → route through `enforceBrowserGuards({ provider: getBridgeBrowser(), action, ... })`
  **before** dispatch (reuse the existing guard call shape from `features/browser/actions.ts:631`),
  then `getBridgeBrowser().sendCommand(...)`.
- **Self-target:** mutating YAAR's own tab stays refused by the existing self-target guard (no new
  code — `isSelf` tab + mutating action → 403). Proposal §3 honored.
- **Consent granularity** (proposal open-Q §9.4): Slice 2 ships **standing per-app T2 grant** (via
  `app.json` `permissions` + first-use dialog) with a **visible action log**, not per-mutation
  prompts. `close` is the only destructive-ish verb; revisit if it feels spooky.

### 2.3 Extension (T2 additions)

- `manifest.json` add `"tabGroups"` permission.
- `background.js`: handle inbound `BridgeCommand` → `chrome.tabs.update({active:true})` (focus),
  `chrome.tabs.remove` (close), `chrome.tabs.group` / `chrome.tabGroups.update` (group),
  `chrome.tabs.move` (move) → reply `BridgeCommandResult { requestId, ok, error? }`.
- Extend `packages/shared/src/bridge.ts`: `BridgeCommand` / `BridgeCommandResult` schemas + bump
  `BRIDGE_PROTOCOL_VERSION`.

### 2.4 Dock integration (the payoff)

Surface real tabs in the dock beside YAAR windows, focusable/closable/groupable — the "OS metaphor
made literal" from proposal §6. Smallest version: the Tabs app (Slice 1) grows focus/close buttons
wired to the new `invoke`. Full dock integration can follow as its own slice.

### Slice 2 done =
A monitor agent (or the Tabs app) can tidy, focus, close, and group the user's **real** tabs, each
mutation gated by the existing per-origin consent + self-target guard, with an action log. Tests:
guard fires on mutating verbs; self-target `close` refused; command round-trip + `requestId`
correlation; version bump refuses old extension.
